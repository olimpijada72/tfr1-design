    Project plan · Revision two

    The BioNeMo Route

    The original plan spent its whole budget on one generation run because that was all it could afford. If NVIDIA's hosted endpoints carry the load, generation stops being the expensive stage, and the money buys something the first plan could not: a second attempt. This revision restructures the pipeline around that possibility, and adds a repair step for the designs the histidine scan breaks.

    00

    What changes, and what does not

    Two tools from the survey earn a place here, and they act at opposite ends of the pipeline. BioNeMo's agent toolkit reopens the engine decision in stages 2 to 4, where it may remove both the setup risk and most of the cost. ArcRefine adds a repair step at stage 5, where the plan currently discards every histidine variant that breaks its own interface.

    Everything else survives intact. The funnel shape, the decision to install the pH switch late rather than early, the portfolio allocation across twenty slots, and the argument for short binders are all unaffected, and this document does not relitigate them.

    The headline is not that BioNeMo is a better engine. It is that moving generation onto hosted endpoints converts the budget from the thing that limits the plan into a reserve, and the first use of that reserve should be a second generation run after stage 4 has shown us what the cross-species gate actually kills.

    That possibility is conditional on one unknown, which is whether the hosted endpoints will serve the volume this pipeline needs. Section 03 is a probe designed to answer exactly that, today, before anything else is committed.

    01

    The engine decision, restructured

    Version one framed this as a choice between two options. BindCraft was picked over assembling RFdiffusion, ProteinMPNN and AlphaFold by hand, and the deciding argument was not quality but setup risk: three codebases and three dependency stacks is how you lose a Tuesday evening to a CUDA version conflict.

    The BioNeMo toolkit attacks that argument directly, because it ships the three-tool route pre-orchestrated and can run the models as hosted services rather than local installs. If that works, the objection that settled version one no longer applies.

    What it does not do is make the choice binary again. There are now three ways to run the same pipeline, and they differ in cost and in what can go wrong, so the right structure is a ladder that we descend only when a rung fails.

    Decision
    Try rung 1 today, install rung 3 tonight

    BindCraft still gets installed this evening whatever the probe says, because it is the only engine we can be certain works by Monday and the install costs an evening we have already budgeted. It is not the plan; it is the thing that stops a failed probe from costing us the week.

    03

    Today's probe

    Everything above is conditional, and today is the day the condition gets tested. The survey proposed a two-hour spike whose success criterion was one binder designed end to end against NVIDIA's own example target. That is the right first probe and it is not sufficient on its own, because it answers whether the thing works and not whether it will work at the scale this pipeline needs.

    A workflow that designs one binder beautifully and then rate-limits at fifty is worse than useless to us, because we would discover it on Wednesday with the budget already spent elsewhere. Throughput is the thing to measure, and it has to be measured today.

    Probe A · Does it run at all

    Install the protein-binder-design skill and run the workflow against NVIDIA's own example target, not TfR1. Substituting our target here conflates two unknowns, and if it fails we will not know which one broke.

    Pass: one binder, designed and co-folded and scored, end to end. Budget 90 minutes.

    Probe B · Will it carry the volume

    Immediately after A succeeds, submit a batch large enough to find the ceiling. Request a few hundred designs and watch what happens: record wall-clock time per design, whether throughput degrades, and whether anything returns a quota or rate-limit error. Keep the exact error text.

    Pass: a sustained rate that reaches thousands of designs inside one overnight run. Budget 30 minutes of wall-clock watching, longer if it is simply slow rather than blocked.

    04

    Stages 1 to 4 under the new engine

    Target prep is unchanged, with one note

    Everything version one specified still holds: cut 1CX8 to roughly residues 189 to 383, confirm the boundaries in PyMOL rather than trusting the numbers, reduce to one chain, strip every heteroatom, and align the mouse span from Q62351. It remains free, it remains the highest-leverage evening in the project, and getting it wrong still poisons everything downstream.

    The one difference is the form the hotspots take. BindCraft wanted them in its own config; the BioNeMo workflow resolves a target and its hotspots as structured input to the skill. The three conserved apical positions are the same three either way, so this is a formatting question rather than a scientific one, but it is worth writing them down in both forms this evening so the Monday launch is not blocked on a syntax question.

    The filters come for free, and that matters more than it sounds

    Version one allocated an afternoon to wiring in ipSAE, on the grounds that the default confidence score spreads itself across the whole system and therefore barely moves when the thing we actually designed is a seventy-five residue binder against a hundred and ninety-five residue target. That argument is unchanged and still correct.

    What changes is that the BioNeMo workflow already ranks on ipSAE alongside ipTM, pLDDT and apo-to-holo RMSD, which is very nearly the exact stack version one specified. We get the better metric without building it.

    Where the saved afternoon should go

    Not into another tool. Put it into probe B above, and into the cross-species gate, which remains the stage that removes half to three quarters of the pool and therefore deserves more care than the one that removes a third.

    The cross-species gate is unchanged in substance

    Re-predict every survivor against the mouse apical sequence and keep only what is confident in both species. Whether that prediction runs on a hosted Boltz-2 endpoint or a local one does not change the logic, the expected attrition, or the reason the plan over-generates in the first place.

    05

    Stage 5, with repair

    This is where ArcRefine enters, and it is the more interesting of the two changes because it alters the structure of the stage rather than merely where it runs.

    The problem version one identified and then accepted: you graft a histidine into the core of a working interface, and the most likely single outcome is that you have just destroyed that interface. The histidine is a different size and shape from whatever it replaced, and the surrounding residues were packed against the old one. Version one's only response was to discard the variant and move on, which is expensive by Friday when the pool is a few dozen designs deep and every loss is a submission slot that stays empty.

    ArcRefine's claim is that it can re-optimise a binder's sequence while holding its binding pose, by predicting the complex once and then carrying that structural information forward through each subsequent sequence update rather than rediscovering the pose every round. Applied here, that turns a discard into a repair: keep the pose, keep the histidine, rebuild everything around it.

    Two ways this goes wrong

    Both follow from the same fact, which is that ArcRefine optimises for binding and we do not actually want the best binder available.

    It will remove the histidine if you let it. A histidine in an interface core is, from a pure affinity standpoint, a poor residue choice, and that is precisely why grafting one breaks things. A sequence optimiser pointed at this variant and left unconstrained has an obvious move available, which is to mutate the histidine back into something that packs well, and it will report a greatly improved binder that no longer does the one thing we needed.

    So the histidine positions must be pinned as immutable before refinement starts. Whether ArcRefine supports fixed positions is not stated on its page, and this is the first thing to check in the two-hour window. If it cannot constrain positions, it is useless for this purpose and should be abandoned immediately, not worked around.

    The second failure is subtler and has no switch to flip. Version one argued for binders of sixty-five to ninety residues on the grounds that a small binder is forced to concentrate its grip, and a concentrated interface is the only kind a single protonation can break. A refinement pass that improves binding works directly against that, burying more surface and spreading the energy more thinly, which walks the design out of the narrow viable band and into the zone where it binds at both pH values and fails requirement three.

    The mitigation is to treat refinement as repair rather than improvement. Run the minimum number of passes that restores a foldable interface and stop there, and if a repaired variant comes back with markedly better predicted affinity than its parent, treat that as a warning sign rather than a success.

    The rest of stage 5 is as version one wrote it. Rank candidate positions by what they sit beside, preferring a histidine that lands next to an arginine or lysine so that protonation creates active repulsion rather than merely removing a favourable contact. Score with PROPKA and FoldX while remembering that neither was built for designed interfaces, and use them to rank structurally sound candidates rather than to rescue failed ones.

    06

    The money, reallocated

    Version one's budget was a single line item: roughly a hundred rentable hours on an L40S, of which it planned to spend fifty to sixty on one generation run and hold the rest back. The reserve existed because the probability that a first run on an untried target is also the last run is low.

    If the hosted route holds, that arithmetic changes shape entirely. Stages 2 to 4 stop consuming GPU hours, and the budget becomes available for things version one could not contemplate.

    The second run is the point

    Version one's sharpest constraint was that it could afford one generation run, which meant the cross-species gate at stage 4 was a thing that happened to the pool rather than something the pool could be designed against. Whatever survived, survived.

    With generation close to free, a second run becomes possible, and it should be aimed rather than simply repeated. The first run tells us which regions of the apical patch produce designs that survive the mouse gate, and the second can concentrate hotspot selection there. That is a genuine improvement in expected quality and not merely more volume.

    Carried over unchanged from v1

    Stop the instance whenever you walk away, because one idle GPU overnight is about twenty dollars and this remains the most common way credits vanish. Put everything on a persistent volume on day one. Run stages 1, 5 and 6 locally, since none of them need a GPU and together they are most of the actual working hours.

    The caveat that has not moved

    Neither of these tools makes requirement three measurable. BioNeMo generates and filters faster and more cheaply; ArcRefine recovers variants that would otherwise be lost. Neither one can tell us whether a histidine will actually release at pH 6.0, because no model in either pipeline represents pH at all.

    We are still engineering requirements one and two, and still sampling requirement three. A better engine means more and better designs to spread the histidine bets across, which is a real gain, and it is not the same thing as de-risking the bet.

    The success criterion from version one therefore stands without amendment. Twenty designs that bind both species tightly, carrying a deliberate and documented spread of histidine placements, is a good submission even if none of them switch, because it is the version of this experiment that returns an interpretable result either way.
